### M-1（medium）uat F-12：未設 `CDP_TRUSTED_PROXIES` 時預設信任私有網段與 loopback，代理沒有覆寫 XFF 或使用者在內網時，可以偽造來源 IP 繞過登入限速
- 位置：`api/src/main/resources/application.yml:51-52`（預設 internal-proxies = 10/8、192.168/16、172.16/12、127/8、::1）；`ClientAddress.java:17-18`；`LoginRateLimiter.java:153-155`、`:185-187`（兩層計數都以來源 IP 為鍵）；契約 `auth.md` §3「來源 IP」；`.env.example:74-75`
- 機制（Tomcat RemoteIpValve 官方文件，經 context7 確認）：連線端位址符合 internal-proxies 時，valve 會**由右往左**讀 `X-Forwarded-For`，符合 internal-proxies 的位址一律略過，第一個不符合的就當成用戶端 IP。所以只要「連線端」和「XFF 裡最右邊的真實位址」都落在私有網段，攻擊者自己填在最左邊的值就會被當成來源 IP
- 攻擊情境（任一成立即可，都不需要任何憑證）：
  1. **代理把 XFF 原樣轉送**：正式環境用 nginx 做 TLS 終結，只寫了 `proxy_pass`、沒有 `proxy_set_header X-Forwarded-For …`。nginx 預設會把用戶端自帶的 XFF 原樣轉給後端，後端看到的連線端是 nginx（loopback 或私有 IP，被信任）。網際網路上的攻擊者每個請求帶一個隨機的 `X-Forwarded-For`，每次都算是新來源：「email＋IP」的 5 次和來源總量的 30 次都形同沒有，唯一的限制是全域併發（CPU 核心數 × BCrypt 速度）。以 4 核、BCrypt cost 10 粗估，每秒約數十次、每天數百萬次猜測，可以對已知 email 做密碼噴灑或撞庫。密碼規則只要求 12 字、不檢查複雜度（`auth.md` §3），弱密碼的帳號會被接管，接著讀取全部客戶個資（VIEWER 以上）
  2. **使用者或攻擊者在內網**：即使代理正確「附加」XFF，內網用戶端的真實 IP（例如 10.x）也在 internal-proxies 裡，valve 會略過它、繼續往左讀攻擊者偽造的值。內部人員或已進入內網的攻擊者可以得到跟情境 1 一樣的效果
  3. **入口做了 SNAT**：L4 負載平衡、Kubernetes `externalTrafficPolicy: Cluster`、Docker userland-proxy 等，會讓外部連線看起來來自私有 IP，而且不改 HTTP 標頭，結果同情境 1
  4. **鎖住他人**（跟驗收條件「未登入者無法以大量登入請求鎖住他人帳號」衝突）：在上述情境下，攻擊者知道受害者的出口 IP（例如公司辦公室），就可以偽造那個 IP 送 30 次錯誤密碼，整個來源的所有帳號都被鎖 15 分鐘；只要每 15 分鐘重送一次，就能一直鎖下去
- 判級：medium。攻擊成立要看部署設定（代理怎麼處理 XFF、入口有沒有 SNAT、使用者是不是在內網），而 repo 裡沒有正式環境的部署設定，DESIGN-05「需調查 2」也還沒結案。攻擊者拿到的是「不受限的線上猜密碼」，不是直接取得資料。不過 v0.2.0 只用 email 計數，偽造 IP 沒有用；在上述情境下，v0.3.0 的防護比 v0.2.0 還弱。如果正式環境確定是情境 1 或 3，應該升為 high
- 預設值要不要收緊：**要**。uat 是從 loopback 直接連線重現的，正好落在預設信任範圍內。不過單純把預設縮成「只信任 loopback」或「全部不信任」都有副作用：同機的 nginx 原樣轉送時照樣可以偽造；全部不信任則讓所有使用者共用代理的 IP，任何人送 30 次錯誤密碼就能鎖住所有人。建議：
  1. 移除寫死的預設值，`CDP_TRUSTED_PROXIES` 改成必填。直接對外的部署填明確代表「不信任任何代理」的值（例如 `-`，實作時把它換成不會符合任何位址的正規式）；有代理的部署只填代理的確切位址，不填整個網段。未設定時拒絕啟動，跟金鑰強度檢查同一種做法
  2. 部署文件（維運手冊或 `.env.example` 註解）寫明代理必須**覆寫**而不是轉送 XFF（nginx 單層代理用 `proxy_set_header X-Forwarded-For $remote_addr;`）。DESIGN-05「需調查 2」要在發版前跟代管維運確認
  3. 驗收測試目前靠「預設信任 loopback」來模擬不同來源（`LoginSourceLimitAcceptanceTest`、`LoginGlobalConcurrencyAcceptanceTest`），改成必填之後要在 `application-test.yml` 明確設定
  - 改變信任範圍屬於安全設定，但這是收緊不是放寬，依 CLAUDE.md 決策分級，收緊不需要 D-編號。是否在本版做，由 manager 決定；因為 H-1 本來就要延後發版，建議一併做

### M-2（medium）IPv6 來源以完整位址計數，一台主機就能輪換無限多個來源
- 位置：`ClientAddress.java:17-18`（直接用 `getRemoteAddr()` 的完整字串）；`LoginRateLimiter.java:153-155`、`:185-187`
- 情境：後端預設綁定所有位址（雙協定）。正式環境的入口如果接受 IPv6，任何一台 VPS 通常都拿得到一整段 /64（2^64 個位址）。攻擊者每個請求換一個來源位址，每個位址都有自己的「email 5 次、總量 30 次」額度，效果跟 M-1 一樣：只剩全域併發限制，可以無限猜密碼。這不需要部署設定出錯，只要 IPv6 可以連到就成立
- 修法：計數鍵依位址族群正規化：IPv4 用完整位址，IPv6 截到 /64 前綴（同一段 /64 共用計數）。也可以在代理層用相同粒度限速。要不要加一層依 email 的寬鬆全域上限（例如每小時 N 次，不論來源），會改到 D-084 的行為，屬於決策分級④，要問甲方

- 修法：使用者建立與角色變更寫稽核紀錄（`created_by`／操作者、時間）；核准時如果送審者帳號是在 N 天內由核准者建立的，就拒絕或提示。要不要做由甲方決定（權限屬決策分級④）

### L-2（low）CI 的 coverage 步驟先跑 PR 程式與第三方套件，同一個 job 之後才用 AE_TOKEN
- 位置：`.github/workflows/ci.yml:111`（`make coverage`，會執行 PR 的測試和 npm、Maven 套件）→ `:122-129`（同一個 job 用 `secrets.AE_TOKEN` checkout agent-engineering）
- 情境：前面步驟執行的程式（惡意的 dev 相依、或有推送權限的人寫的測試）可以寫入 `$GITHUB_ENV`／`$GITHUB_PATH`，例如設定 `NODE_OPTIONS=--require …`，或在 PATH 前面插一個假的 `git`。後面的 `actions/checkout` 執行時就會帶著 token 跑攻擊者的程式碼，把 AE_TOKEN 外傳。`persist-credentials: false` 只保證 token 不留在磁碟，擋不住這種做法。fork 來的 PR 拿不到 secrets，所以只有同 repo 的分支和供應鏈攻擊是可行路徑
- 判級：low。依 `ci.yml:154` 的說明，AE_TOKEN 是 fine-grained token，只有 agent-engineering 的 Contents 唯讀權限；外洩只會讓私有工具 repo 被讀走
- 修法：把 coverage-gate 拆成獨立的 job，在 check job 之後執行、透過 artifact 取得 coverage XML，這樣執行 PR 程式的 job 裡就沒有 secret；或者在 checkout agent-engineering 之前先執行 coverage-gate 需要的步驟。`ci.yml` 不屬於範本流程檔，由 architect 處理

- 「email＋IP」的維度（D-084）：跟受害者共用同一個出口 IP 的人（同一個辦公室 NAT），仍然可以鎖住受害者在那個來源的帳號，也可以用 30 次失敗鎖住整個來源。這是甲方選的方案 A 的代價
