## 對照設計：有防到的
- 授權矩陣（auth.md §2）：每條路由都有 `AccessRule`，未列的路徑預設 `ADMIN`（`SecurityConfig.java:117-118`）。INGEST、管理金鑰、session 三種憑證用 `CRED_*` authority 區分；只收管理金鑰或只收 session 的 API 都有限定憑證種類（`:73-76`、`:96`、`:103`、`:110-115`）。單一租戶（D-051），沒有「資料擁有者」的維度，所有 VIEWER 依設計都能看全部客戶，所以沒有改 id 越權的問題
- 金鑰比對：先 SHA-256 再用 `MessageDigest.isEqual`，兩把都比、不短路（`SecretMatcher.java:12-17`、`ApiKeyAuthenticationFilter.java:46-51`）。帶了 Authorization 但不符時直接回 401，不會退回去看 session（fail closed）
- session：登入成功先 invalidate 舊 session 再發新的，防 session fixation（`AuthController.java:108-114`）。每個請求都重新載入使用者並比對 `session_epoch`，所以停用、改角色、管理員重設密碼都在下一個請求生效（`SessionAuthenticationFilter.java:53-63`，D-071）。cookie 設 `HttpOnly; Secure; SameSite=Strict; Path=/api`（`application.yml:39-47`）
- CSRF：cookie、session 內存值、標頭三者一致才放行（`SessionCsrfTokenRepository.java:47-59`）。認證 filter 排在 CsrfFilter 前面（`SecurityConfig.java:86-87`），所以 `sessionWriteRequest` 拿得到認證結果，不會因為還沒認證就跳過 CSRF 檢查。login 限 `application/json`（`AuthController.java:66`），跨站表單送不進來；logout 免 CSRF，但 SameSite=Strict 下跨站請求不會帶 cookie。有 `CsrfAcceptanceTest`
- 密碼：BCrypt，超過 72 位元組一律拒絕。帳號不存在也跑一次 dummy BCrypt，回應碼和耗時都一樣（`PasswordHasher.java`、`AuthController.java:96-100`）。`password_hash` 不會出現在回應或 `toString`
- 登入限速（D-045）：佔名額和檢查鎖定是原子操作，同時進行 BCrypt 的請求數不超過門檻（`LoginRateLimiter.java:63-82`）
- 最後一位管理員：先鎖全部 ADMIN 再鎖目標列，同一個交易判定（`UserService.java:104-124`）
- 遮罩（D-014、D-021）：白名單；`attributes`、`identifiers[i].value`、`variables`、`trigger_snapshot`、`trace[].evaluated` 都遮（`PiiMasker.java`）
- 機密與 log：`AuthProperties`、`LoginRequest`、`PasswordChangeRequest`、`Create/UpdateUserRequest`、`AppUser` 都覆寫了 `toString`。JDBC URL 帶 `logServerErrorDetail=false`，DB 錯誤不會把欄位值寫進 log。錯誤回應不回傳例外訊息。前端 bundle 不含任何金鑰或環境變數
- 前端：沒有 `dangerouslySetInnerHTML`。`safeNext` 擋掉 `//` 開頭和外部網址，其他路徑走 `history.pushState`，瀏覽器不允許跨源，無法做開放重導向
- 新 migration：V6、V7_1、V7_2 都不含資料或權限變更，V7_2 只重建索引，跟 `due-backlog.md` 的「威脅與對策」一致

## 發現

### M-1（medium）後端照收佔位值或極短的 API 金鑰
- 位置：`api/src/main/java/com/cdp/security/AuthPropertiesValidator.java:17-30`；佔位值的來源是 `.env.example:46-48`
- 情境：維運照 `.env.example` 建 `.env`，只換了 `CDP_INGEST_API_KEY`，`CDP_ADMIN_API_KEY` 留著 `CHANGE_ME`（或填了 `admin`、`test` 這類短值）。後端只檢查「不可空白」和「兩把不可相同」，照常啟動。任何連得到 API 的人送 `Authorization: Bearer CHANGE_ME`，就拿到 `ADMIN`：讀全部客戶與軌跡、`POST /users` 建自己的管理員帳號、重設他人密碼
- 現有緩解：`ae check-env` 會標出 `CHANGE_ME`，但那是開發流程工具，不是後端啟動時的保證；兩把都沒改時，相同值檢查會擋下
- 修法：`AuthPropertiesValidator` 遇到值含 `CHANGE_ME`、或長度低於下限（建議 ≥ 32 字元）就拒絕啟動，錯誤訊息只寫設定名稱；並補啟動驗收測試

### M-2（medium）未登入的人可以持續鎖住任何已知帳號，並用大量登入請求消耗 CPU
- 位置：`api/src/main/java/com/cdp/security/LoginRateLimiter.java:63-82`（只以 email 為維度）、`:65-66`（超過 10,000 筆後每次請求都掃整張表）；`AuthController.java:86-100`；契約 `auth.md` §3 明訂「不依來源 IP」（D-045）
- 情境 1（鎖帳號）：攻擊者不需要任何憑證，只要知道或猜到管理員的 email，每 15 分鐘送 5 次錯誤密碼，該帳號就永遠處在 `429`。對所有猜得到的 email 都能這樣做，讓整間公司的人登不進去。管理金鑰不受影響，但一般操作中斷
- 情境 2（CPU）：每次用新 email 嘗試都會跑一次 BCrypt，沒有任何全域或依 IP 的上限。15 分鐘內累積超過 10,000 筆有效紀錄後，`tryBegin` 每次都要 `removeIf` 掃整張 map，請求成本隨筆數線性上升
- 判級：可用性問題，不會洩漏資料，也不會讓人越權，所以是 medium。依 email 計數是 D-045 定案的設計
- 修法（要改維度屬決策分級④，需由 manager 問甲方）：在反向代理或應用層加依來源 IP 的全域限速；改成漸進延遲而不是硬鎖；掃描只在新增紀錄時做，或改用有上限、可淘汰的快取

### L-1（low）VIEWER 可以用完全比對搜尋，確認或查出被遮罩的識別碼
- 位置：`api/src/main/java/com/cdp/profile/ProfileSearchService.java:96-148`（D-048 完全比對）、`ProfileController.java:42-45`
- 情境：遮罩（D-014）是要讓檢視者看不到客戶的明文 email、手機。但 VIEWER 輸入一個猜測的手機或 email，有結果就證實「這個人是我們的客戶，識別碼就是這個值」。搜尋沒有限速，也沒有稽核紀錄，內部人員可以寫腳本大量比對
- 修法：搜尋加稽核 log（誰、何時、查了哪個 hash，不記明文）和依使用者的限速；是否限制 VIEWER 能用的搜尋方式，需由甲方決定

### L-2（low）`/auth/password` 沒有嘗試次數限制
- 位置：`api/src/main/java/com/cdp/user/UserService.java:129-143`；契約 `auth.md` §3「範圍」把它排除在限速外
- 情境：攻擊者拿到一個有效 session（例如沒鎖螢幕的電腦）後，可以無限次猜 `current_password`。猜中就能改掉密碼，取得 session 逾時之後仍然有效的憑證，原使用者也被擋在外面
- 修法：`/auth/password` 套用同一個 `LoginRateLimiter`（以 user_id 為鍵），或連錯 N 次就讓這個 session 失效

### L-3（low）demo-seed 在任何環境都會建立、重設並重新啟用一個 ADMIN 示範帳號
- 位置：`tools/demo-seed/seed.py:88-109`（`demo-admin@example.com`；已存在時會 PATCH，把狀態改回 `ACTIVE` 並換掉密碼）
- 情境：有人在客戶環境（只要在 127.0.0.1 上就連得到）誤跑 `make demo-seed`，就會多出一個管理員，密碼是 `.env` 裡的 `CDP_DEMO_PASSWORD`，或是印在終端機上的隨機值。維運之前停用的示範帳號也會被重新啟用。要跑這個工具本來就需要管理金鑰，所以算是操作失誤造成的後門，不是外部可直接利用的漏洞
- 修法：預設不建 ADMIN 示範帳號，要另外加明確旗標才建；或者偵測到已有非 demo 使用者時就停止並提示

### 已知設計取捨（不計入發現）
- 使用者自己改密碼時，其他裝置不會被登出（`auth.md` §3、D-071 定案）
- 請求大小不設上限（D-023）：限 INGEST 金鑰和管理金鑰的 API 才受影響
- session 只有閒置逾時，沒有絕對上限（`CDP_SESSION_IDLE_TIMEOUT`），後端重啟後全部失效
